# Native plugins and package installation

Graphite API v1 plugins run either as JavaScript in one system Node.js 24+ process per plugin (`"runtime": "node"`, the default) or as a compiled native executable built with `graphite-plugin-sdk` (`"runtime": "native"`, no Node.js required). TypeScript is compiled before packaging. `graphite-plugins` owns manifests, ZIP validation, installation and scaffolding without depending on GPU/application types. The application owns plugin sidebar state, workbench contributions, lazy activation and session routing; its existing services apply changes on the event loop.

## Runtime boundary

For Node.js plugins, the bundled CommonJS host (`host-v1.cjs`) loads the plugin's JavaScript entry and calls `activate(context, graphite)`. Both ES modules and CommonJS exports are supported, and `deactivate()` is optional. For compiled native plugins (`"runtime": "native"`), Graphite spawns the executable directly with the plugin directory as its first argument and uses `graphite-plugin-sdk` (`Plugin` + `run_plugin`). Both runtimes share protocol v2 framing, handshake, bounded queues, deadlines, cancellation and resource disposal from [Services and simulated host](services-host.md). Stdout is reserved exclusively for framed messages; console/log output goes to stderr and is captured per plugin under `logs/<id>/console.log`.

Each plugin process owns its supervisor, commands, document subscriptions, tree/webview providers, language providers, terminals, chat tools, request IDs and session. Commands, views, menus and keybindings must be declared in `graphite-plugin.json`, scoped by the plugin ID, and cannot shadow built-ins.

API v1 exposes:

- **Commands & Documents:** `commands` (`list`, `execute`, `registerCommand`), `documents` (`list`, `open`, `save`, `snapshot`, `applyEdits`, `onDidChange`, `onWillSave`). Document changes retain UTF-16 range validation, read-only checks, atomic edits and undo.
- **Workbench UI & Storage:** `window` (`showMessage`, `focusView`, `showInputBox`, `showQuickPick`, `createStatusBarItem`, `createOutputChannel`, `registerTreeDataProvider`, `createWebviewPanel` with sandboxed CSP/message passing), plus `storage.global` and `storage.workspace` JSON persistence.
- **Editor & Languages:** `editor` (`active`, `setSelections`, `createDecorationType`, `setDecorations`), `languages` (`setDiagnostics`, `clearDiagnostics`, `registerCompletionProvider`, `registerHoverProvider`, `registerFormattingProvider`), and declarative `themes`, `snippets` and `languages` (comment tokens/extensions) in the manifest.
- **System APIs:** `terminal` (`create`, `sendText`, `show`), workspace-confined `workspace` FS (`findFiles`, `readFile`, `writeFile` rejecting `..`, symlinks outside the workspace and `.git/`), `scm.status`, and `chat.registerTool` (surfacing plugin tools to Chat turns alongside approval checks).

## Granular permissions & development workflow

Manifests support a `permissions` array with canonical capability tokens: `commands`, `documents.read`, `documents.write`, `ui`, `languages`, `storage`, `workspace.read`, `workspace.write`, `terminal`, `chat` and `*`. Privileged system capabilities (`workspace.read`, `workspace.write`, `terminal`, `chat`) are denied unless explicitly granted in `permissions`. Standard editor capabilities remain permitted when `permissions` is omitted for backward compatibility, and are strictly enforced whenever `permissions` is non-empty.

For local iteration, `graphite plugin dev <dir>` links a plugin directory directly in development mode with live mtime watching on `graphite-plugin.json` and the entrypoint for automatic hot reload; `graphite plugin unlink <id>` removes the dev link cleanly without touching the source folder. `activationEvents` (`*`, `onStartupFinished`, `onCommand:<id>`, `onLanguage:<lang>`, `onView:<viewId>`) avoid starting inactive plugins until needed.

Disabling, replacing or removing a plugin clears its registrations, UI contributions, chat tools and pending work without stopping other hosts or LSP. Manual restart creates a new session. Normal shutdown gives `deactivate()` a bounded opportunity to run before terminating the process. A process boundary isolates crashes, not malicious OS code: enable only trusted plugins.

## Packages and persistent state

Native packages are ZIP files ending in `.graphite-plugin`, with `graphite-plugin.json` at their root. VSIX packages are read through `extension/package.json`. Installation never runs npm, lifecycle scripts or package code. The Plugins sidebar searches Open VSX, downloads the latest VSIX, validates it and confirms before installation. Executable VSIX packages use the [Code OSS runtime](extension-compat.md). Profile stores keep installations and trust approvals separate.

The user configuration directory contains `plugins/`, `logs/`, per-plugin JSON records and immutable version directories. Installation validates and extracts into a fresh staging directory (restoring Unix `0o755` executable mode for native binary entrypoints and resolving `.exe` on Windows), then atomically replaces the registry record. A failed publication retains the previous record and package. Previous directories remain available to live hosts until removal; removal matches an exact plugin identity boundary. Every successful installation starts disabled with no trusted version, including updates and reinstalls. Trust is recorded for the installed version. Open VSX updates confirm the downloaded archive identity and version against registry metadata before replacing the installed record.

VSIX packages are limited to 1 GiB compressed, 4 GiB expanded, and 100,000 archive entries. Native `.graphite-plugin` packages are limited to 100 MiB compressed, 500 MiB expanded, and 10,000 archive entries. Open VSX and Graphite stream downloads to temporary files and check the received size. Absolute/traversing paths, Windows aliases, duplicate paths, case collisions, file/directory collisions, symlinks and special files are rejected. Failed installation removes staging data. Packing excludes hidden files and `target`, rejects sensitive key/database file extensions and links, and validates the runtime-appropriate entrypoint (`.js`/`.cjs`/`.mjs` for `node`, or a relative binary path for `native`).

## Discovery and UI

The Plugins sidebar opens with `Ctrl+Shift+X` or `graphite.plugins.open`. It reuses the 260 px workbench sidebar next to the activity bar, so the editor remains visible. The sidebar owns keyboard input only while focused; the editor, Quick Open, find, project search, Source Control, the terminal and confirmation surfaces keep precedence otherwise. Filesystem, network and Node startup checks run on workers. The Open VSX search client loads up to 30 results and uses HTTPS for the public registry. The additive Graphite tab searches public GitHub repositories with the `graphite-plugin` topic and the current text query. It lists repositories even when they do not yet have a compatible release asset. Opening a repository loads its latest stable release and offers `.graphite-plugin` and `.vsix` assets for inspection; the user chooses when multiple assets exist. Downloads remain size-limited, and the final redirected URL must use HTTPS on GitHub's download hosts.

Selecting an Open VSX result downloads its latest version to a temporary file for inspection. Clicking or pressing Enter on a Graphite repository opens one editor detail tab per repository. The page requests GitHub's rendered README representation (with the GFM Markdown endpoint as a fallback) and displays it in a sandboxed WebView with GitHub-style dark colors, headings, code, tables, task lists and HTTPS images, alongside stars, compatible release download totals, release assets and project links. Relative images resolve from the repository README. Scripts, forms, frames and non-HTTPS images are blocked; HTTPS links open externally. Installation and VSIX updates use the local package validator and require confirmation. Updates reset enablement and version trust. Native Graphite plugins still require explicit version trust and workspace trust before execution; revoking workspace trust stops active plugin hosts and tasks. VSIX activation uses the same workspace gate and its own Code OSS session. Local package installation remains available offline.

Tests use isolated directories, a local HTTP server, real Node fixtures and compiled native binaries via `graphite-plugin-sdk`. See [Plugin development](../contributing/plugins.md) for the manifest, SDK and controls.
